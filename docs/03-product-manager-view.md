# AI 产品经理视角：电商售后问答 Agent

> 同一个项目，从产品经理的角度，不只看“用了什么模型”，更看“解决谁的问题、哪些问题该自动、失败时谁兜底、如何证明它有用”。

## 1. 一句话产品定义

面向中小电商售后场景，提供**有知识依据、能查询订单物流、在不确定时转人工**的 AI 客服助手，并为运营人员提供可观察、可干预的工作台。

## 2. 为什么选售后，而不是泛知识问答

售后是适合 AI 落地的场景：

- 重复问题多，FAQ 和售后政策相对稳定；
- 订单和物流实时变化，适合用工具补齐；
- 用户问题带上下文，能体现多轮对话价值；
- 错误成本高，正好练习“置信度、引用、拒答、转人工”这些产品边界。

但售后也有明显风险：

- 不能胡乱承诺退款或赔付；
- 不能泄露其他用户订单；
- 不能把政策说成法律保证；
- 模型不知道订单实时状态。

因此产品核心不是“让模型自由发挥”，而是：

> **知识给依据，工具给事实，人工给兜底。**

## 3. 用户与任务

| 用户 | 核心任务 | 产品需要提供什么 |
|---|---|---|
| 消费者 | 快速知道能不能退、订单到哪、政策怎么算 | 自然语言问答、引用、订单查询、转人工 |
| 客服/运营 | 审核 AI 回答、接手复杂问题、维护知识 | 会话记录、工具轨迹、引用、工单、知识库 |
| 店铺管理者 | 降低重复咨询与客服成本 | 解决率、转人工率、满意度、成本、知识缺口 |

M1 优先做运营可进入的工作台，是因为 AI 回答必须能被观察和治理，而不是只给消费者一个黑盒聊天框。

## 4. 产品范围与优先级

### 第一版必须做

- 政策和 FAQ 问答；
- 有来源引用；
- 订单/物流查询；
- 售后条件辅助判断；
- 不确定时拒答或转人工；
- 客服能看到引用和工具轨迹；
- 基础运营指标。

### 暂不做

- 真实退款、改地址、赔付：高风险且需要业务授权；
- 全渠道客服：接入成本高，偏离 AI 学习目标；
- 多租户 SaaS：会让权限和数据建模膨胀；
- 多 Agent 自主协作：当前场景不需要，增加不可控性；
- 预测性推荐、营销文案：与售后问题不直接相关。

这体现了一个产品判断：**优先做能验证核心价值的最小闭环，而不是把所有“AI 功能”都塞进页面。**

## 5. 关键产品决策

| 决策 | 取舍 |
|---|---|
| RAG + 工具，而不是只靠长上下文 | 知识更新可控、引用可追溯、成本和延迟更稳定 |
| 单 Agent + 确定性流程 | 相比多 Agent，更好调试，更适合高风险客服 |
| 订单查询只读 | 先保证安全，不接真实资金操作 |
| 引用必须展示 | 让用户和客服都能复核，降低幻觉信任风险 |
| 低置信度转人工 | 不把“必须回答”当作指标，允许说不知道 |
| 先做 Web 后台 | 客服运营场景天然是桌面 Web，移动端 H5 足够 |

## 6. 指标设计

不能只用“回答看起来不错”来证明产品价值。

### 业务指标

- 重复问题自助解决率；
- 人工转接率；
- 单次咨询成本；
- 平均首次响应时间。

### 体验指标

- 有来源回答比例；
- 用户点赞率/点踩率；
- 低分问题人工复核后的可解决率；
- 多轮任务完成率。

### AI 质量指标

- 检索 Recall@5；
- 引用覆盖率；
- 回答事实一致性；
- 工具调用正确率；
- 拒绝回答/转人工的准确率。

这些指标已在 M6 用 50 条自建评测集实测；结果与限制见 [M6 评测报告](05-evaluation-report.md)。

## 7. M1 的产品价值

M1 不是“模型还没接上所以没用”，它完成了产品可治理性的底座：

- 后台有明确的运营身份；
- 订单和商品数据结构稳定；
- 知识和切片可管理；
- 会话、消息、工具、工单都有落点；
- 运营可以看到系统能力进度；
- 所有演示数据是合成的，可以安全公开。

从产品角度，这相当于先把“客服工作台”搭出来，再让 AI 加入。

## 7.1 M2 的产品复盘

M2 表面上是技术里程碑，实际上解决了一个产品信任问题：

> 运营人员凭什么相信 AI 会按店铺的政策回答？

当前给出的答案是三件事：

1. **知识来源可见**：具体来自哪份文档、哪个章节、哪个切片；
2. **索引状态可见**：哪些文档待处理、哪些失败、哪些已经可检索；
3. **失败可干预**：索引失败可以重试，而不是只能看到一句“系统错误”。

知识库页面没有做成“上传即完成”的黑盒，而是明确展示：

- 文档与切片数量；
- 已索引和待处理数量；
- 上传后的自动入库过程；
- Top-K 检索的相似度和原文；
- 每份文档的索引状态。

这直接服务于运营的两种任务：

- 判断某个问题“为什么没答好”；
- 判断应该补哪份知识、重跑哪份索引。

M2 还不支持文档删除、版本回滚和审核发布，这在产品上意味着知识治理还不完整。因此当前不适合真实上线，只适合作为学习和演示闭环。

从指标角度，M2 只证明了**基础召回可用**：

- 抽样问题能命中预期章节；
- 上传新文档后可被检索到；
- 索引失败状态可观察。

它还没有证明“最终回答正确”，这要等 M3 把检索结果交给 DeepSeek 后再测。

## 7.2 M3 的产品复盘

M3 第一次让消费者拿到了完整的产品体验：

- 从首页点击“开始咨询”；
- 直接打开匿名聊天；
- 看到回答逐字出现；
- 点击引用查看政策原文；
- 刷新页面后继续上一段对话；
- 问超出知识范围的问题时，明确被告知“无法确认，建议转人工”。

### 这一阶段真正解决的产品问题

**AI 客服不是“回答越长越好”，而是“在不知道的时候敢说不知道”。**

M3 把信任拆成三个可见部分：

1. **生成过程可见**：回答逐步出现，用户能停止，不是长时间空白等待；
2. **依据可见**：内联引用 + 可展开的资料原文；
3. **边界可见**：低于相似度阈值不调用模型，直接给出保守兜底。

### 关键产品取舍

| 取舍 | 原因 |
|---|---|
| 先做流式文本，不做头像动画/语音 | 优先验证核心问答价值，不把成本花在装饰上 |
| 只显示回答真实引用的来源 | 避免堆砌 Top-5 让用户误以为全部被使用 |
| 低相关直接拒答 | 售后政策错误比“答不出”代价更高 |
| 匿名会话，不做消费者登录 | 降低试用门槛；但随机 ID 不是正式鉴权 |
| 订单问题先安全拒答 | 工具和权限尚未做好，不能先承诺能力 |

### 当前需要持续观察的指标

- 回答开始时间（首字延迟）；
- 完整回答延迟；
- 单轮 token 成本；
- 引用被点击/展开的比例（需要前端事件埋点）；
- “知识库未命中”问题的高频主题；
- 用户后续是否转向人工（M4 有工单后才能准确统计）。

M3 的抽样验收只能说明“链路可用”，不能说明“质量达标”。  
真正的召回率、引用覆盖率和任务完成率已在 M6 评测中量化；但样本仍是合成的，不能等同于线上质量。

### 仍然不能对外承诺的能力

- 查询具体订单或物流状态；
- 创建人工工单；
- 修改地址、退款、赔付；
- 记住跨会话的用户偏好；
- 处理图片、语音和扫描件。

所以 M3 适合作为**内部演示和体验验证**，不适合直接对真实消费者开放。

## 7.3 M4 的产品复盘

M4 让 AI 客服第一次可以“办事”，但产品上最重要的不是工具数量，而是**权限边界**。

### 用户获得的完整路径

- 问订单 → 直接得到订单状态和物流轨迹；
- 问“我这单有划痕能退吗” → 得到基于签收时间和政策来源的辅助判断；
- 不知道订单号 → Agent 先追问，而不是乱猜；
- 要求人工 → 创建真实工单，而不是只说一句“请联系客服”。

### 关键产品决策

| 决策 | 原因 |
|---|---|
| 只读订单/物流 | 先证明查询价值，不把资金和履约风险引入演示 |
| 工具结果不替代政策 | 事实来自业务系统，规则仍来自知识库 |
| 售后判断不直接退款 | 避免 AI 越权；实际售后交给人工工单 |
| 规则路由优先 | 比自由 Agent 更容易预测和控制，适合高风险客服 |
| 工单去重 | 用户反复说“转人工”不应生成多张工单 |
| 工具调用可见 | 让用户和运营知道答案来自系统查询，而不是模型记忆 |

### 产品上的新风险

- **自动化偏差**：用户可能把“辅助判断”理解为“已经批准退款”；
- **工具错误**：订单不存在、物流未生成时，话术必须说清楚；
- **工单积压**：Agent 可以创建工单，但如果没有客服处理，反而伤害体验；
- **权限误读**：查询能力与执行能力必须清楚区分。

M4 通过文案和边界限制降低这些风险，但真正的工单处理闭环要等 M5。

### M4 的可观测指标

- 工具调用率与工具成功率；
- 订单/物流问题的自助完成率；
- 售后判断后转人工的比例；
- 工单创建量、重复率和优先级分布；
- 工具耗时与整体回答延迟；
- 工具错误导致的拒答/澄清率。

目前这些是设计指标，真实统计需要运营面板和更多样本。

## 7.4 M5 的产品复盘

M5 把“能回答”变成了“能被运营”：

- 用户可以对每条回答点赞/点踩；
- 运营可以看到完整会话、工具轨迹和引用；
- Agent 创建的工单进入人工队列，并可以被分配、备注和关闭；
- 低分反馈与知识缺口被整理成待改进信号；
- Token、延迟、工具使用和成本成为产品仪表。

### M5 的核心产品认知

**AI 客服的上限不只由模型决定，也由人类反馈闭环决定。**

没有反馈，团队不知道哪类问题答错；  
没有工单，转人工只是话术；  
没有知识缺口和成本观察，优化没有方向。

### 关键取舍

| 决策 | 原因 |
|---|---|
| 先做单管理员工作台 | 数据模型和流程优先，角色权限留到后续 |
| 反馈只用赞/踩 | 降低用户操作成本，先建立信号 |
| 工单人工处理，不自动退款 | 资金与履约风险不交给模型 |
| 知识缺口从失败回答推导 | 不新增复杂标注系统，先形成可行动列表 |
| 成本明确标注估算 | 避免把演示估值当成财务账单 |

### M5 后仍不能承诺的事

- 真实多客服协作和 SLA；
- 自动根据缺口更新知识库；
- 完整用户身份认证和防滥用；
- 真实订单退款/改地址；
- 对回答质量的统计显著性结论。

M6 的评测会补上“回答质量是否真的提升”，而不仅是有没有反馈。

## 7.5 M6 的产品复盘

M6 表面上是一个技术任务，实际上回答了三个产品问题：

1. 用户的问题是否真的被解决？
2. 为了提升解决率，我们愿意付出多少延迟和成本？
3. 一个“更复杂”的方案，是否值得上线？

### 评测不是技术团队的内部玩具

如果没有固定评测集，产品经理只能听到两种声音：

- “我觉得这个回答变好了”；
- “用户好像不太满意”。

这两种反馈都无法指导优先级。  
M6 把产品验收拆成可观察的指标：

| 产品问题 | 评测指标 |
|---|---|
| 该答的有没有答对？ | 端到端通过率、分类通过率 |
| 依据找对了吗？ | 检索命中、Top-1/MRR、引用覆盖 |
| 工具用对了吗？ | 工具调用正确率 |
| 该拒答时是否安全？ | 安全拒答/澄清率 |
| 用户等多久？ | 平均/P95 延迟 |
| 每次回答多少钱？ | tokens、估算成本 |

### 结果说明了什么

50 条样本、三组配置：

- baseline、Prompt v2、Prompt v2 + Reranker 都完成了 50/50；
- Prompt v2 把平均延迟从 2,780ms 降到 2,394ms，成本从 ¥0.0759 降到 ¥0.0613；
- Reranker 把检索 Top-1 从 15/19 提升到 18/19，但平均延迟增加约 19.5%；
- 端到端通过率没有继续提升。

这说明：

> 当任务完成率已经很高时，继续堆叠更复杂的检索方案，未必能带来用户可感知的价值。

### 产品决策

| 决策 | 理由 |
|---|---|
| 默认启用 Prompt v2 | 通过率不降，延迟、token、成本都下降 |
| 默认关闭 Reranker | 端到端收益不明显，但延迟增加约 20% |
| 保留 Reranker 开关 | 对“首条依据排序”敏感的场景可以按需开启 |
| 把评测脚本纳入仓库 | 下次改 Prompt/模型可以复跑，而不是重新拍脑袋 |
| 不宣称统计显著 | 50 条单次运行不足以支撑强结论 |

### 为什么“通过率 100%”不是终点

如果一版系统在固定评测集上全部通过，可能有两种情况：

1. 系统真的很好；
2. 评测集太简单。

这次更接近第 2 种。  
所以 M6 报告明确写了“通过率饱和”，下一轮要增加：

- 近义政策与相似条款的区分；
- 冲突信息和过期知识；
- 更长、更绕的多轮对话；
- 提示注入和越权请求；
- 同一问题的不同表达方式。

这比把通过率从 98% 刷到 99% 更有产品价值。

### 面试时怎么讲

不要只说“我做了评测集”，要讲决策：

> “我先用 50 条合成样本把知识、工具、拒答和多轮场景固定下来，再把 Prompt 和 Reranker 做成可配置项。结果发现三种配置都能完成任务，但 Prompt v2 把延迟降低约 14%、成本降低约 19%；Reranker 改善了检索首条命中，却增加约 20% 延迟，端到端通过率没有提升。所以生产默认用 Prompt v2，Reranker 只作为可选。这个结论比‘我加了 Reranker’更有价值。”

同时要主动说明：

- 样本是合成的、规模小；
- 单次运行，不宣称统计显著；
- 规则评分不能完全替代人工评审；
- 真实上线后还需要线上指标和人工抽检。

## 8. 风险与应对

| 风险 | 产品应对 |
|---|---|
| 模型编造售后政策 | 强制检索；展示引用；无依据拒答 |
| 用户要求真实退款 | 不开放真实资金工具；转人工 |
| 订单隐私 | 先验证订单号；展示脱敏信息 |
| 免费 API 限速 | 批量请求、跳过已成功切片、失败重试；正式版本再增加向量缓存 |
| 知识过期 | 保存版本与生效日期；当前需重新索引，删除/回滚尚未实现 |
| 运营不信任 AI | 展示引用、工具轨迹和低置信度标记 |

## 9. 面试如何讲

不要从“我用了 DeepSeek 和 Chroma”开始，先讲问题：

> “我选择电商售后，是因为它同时包含稳定知识和实时业务数据。只做 RAG 会答不了‘我的包裹在哪’，只做 API 查询又答不了政策。所以我把问题拆成知识检索、业务工具和人工兜底三部分。”

然后讲取舍：

> “第一版没有做真实退款，也没有追求多 Agent。售后是高风险管理场景，确定性工作流、引用和转人工比‘自主性’更重要。”

最后讲验证：

> “我建立了评测集，分别看检索命中、引用覆盖、工具正确率和转人工触发。数字会在评测后填入简历，而不是估一个。”
